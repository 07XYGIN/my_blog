```sql title="vector_demo.sql" showLineNumbers
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE vector_demo (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    content TEXT NOT NULL,
    embedding VECTOR(3) NOT NULL
);

INSERT INTO vector_demo (content, embedding) VALUES
    ('示例 A', '[1, 0, 0]'),
    ('示例 B', '[0.8, 0.2, 0]'),
    ('示例 C', '[0, 1, 0]');

SELECT id, content,
       embedding <=> '[1, 0, 0]'::vector AS cosine_distance
FROM vector_demo
ORDER BY embedding <=> '[1, 0, 0]'::vector
LIMIT 2;
```

## 安装前提与维度

示例使用 PostgreSQL 13+，扩展需先安装在数据库服务器上；可选用已包含 pgvector 的服务或镜像，再由有权限的账号执行 `CREATE EXTENSION`。它只为当前数据库启用扩展，不会下载缺失的服务器文件。可以通过 `SELECT extversion FROM pg_extension WHERE extname = 'vector';` 查看启用版本。

上面是独立的教学脚本，表名需要尚未存在。三个坐标是手写演示数据，不能用于真实语义搜索。实际使用时，通过同一个 embedding 模型和同一套配置生成文档向量与查询向量，把 `VECTOR(3)` 改为实际输出维度。维度由模型与参数确定，不存在“某类模型一定是 768 维”的通则。

Python 等应用通过驱动传参写入向量，不要把用户输入直接拼成 SQL。模型更新时也要区分向量空间，即使维度相同，来自不同模型的向量也不能直接比较。

## 距离与查询方向

| 运算符 | 含义 | 检索时的排序 |
| --- | --- | --- |
| `<->` | L2 欧氏距离 | 升序，越小越近 |
| `<=>` | 余弦距离 | 升序，越小越近 |
| `<#>` | 负内积 | 升序，相当于内积越大越前 |

如果需要展示余弦相似度，可以计算 `1 - (embedding <=> query_vector)`；排序仍保留距离运算符的升序形式以匹配索引。余弦相似度的数学范围为 -1 到 1，不能无条件当成 0 到 1 的概率。

小表不建向量索引即可执行精确搜索。余弦查询不要写入零向量：零向量没有定义良好的余弦方向，也不会被余弦 HNSW 索引收录。

## HNSW 索引与使用边界

数据量较大时，可以在已有表上建立与距离运算符匹配的近似索引。HNSW 需要 pgvector 0.5.0+：

```sql title="cosine_index.sql"
CREATE INDEX idx_vector_demo_embedding_cosine
ON vector_demo USING hnsw (embedding vector_cosine_ops);

EXPLAIN
SELECT id, content
FROM vector_demo
ORDER BY embedding <=> '[1, 0, 0]'::vector
LIMIT 2;
```

`vector_cosine_ops` 对应 `<=>`；L2 使用 `vector_l2_ops`，内积使用 `vector_ip_ops`。需要按索引支持的距离表达式排序并带 `LIMIT`，优化器才有机会选择近邻索引。三行演示表很小，执行计划选择顺序扫描很正常。

HNSW 是近似搜索，结果和精确搜索可能不同，并会增加建索引时间与内存占用。带元数据过滤时还需要检查召回数量和执行计划。标准 `vector` 类型的 HNSW 索引支持最多 2,000 维，不能认为所有 embedding 输出都能直接建立这个索引；高维数据应结合扩展版本研究 `halfvec` 等方案并评估精度。

真实检索还需要分段策略、模型一致性和效果评估。这段 SQL 只覆盖向量存储与近邻查询，不包含生成 embedding 或完整 RAG 流程。
