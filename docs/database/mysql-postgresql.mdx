这篇记录 MySQL 8.0 与 PostgreSQL 13+ 的常用差异。通用的查询、连接和事务概念见[数据库公共知识](/blog/sql-basics)，向量检索另见 [pgvector 速查](/snippets/database/pgvector)。两个数据库的代码分别执行，不要在同一连接中混用。

## 数据库与表结构查看

MySQL 客户端中使用 SQL 切换数据库：

```sql title="MySQL"
SELECT VERSION();
SHOW DATABASES;

CREATE DATABASE IF NOT EXISTS learning
    DEFAULT CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci; -- MySQL 8：比较时忽略重音和大小写
USE learning;

SHOW TABLES;
DESC users;
SHOW CREATE TABLE users;
```

`utf8mb4_0900_ai_ci` 是 MySQL 8 的排序规则，其中 `ai` 表示不区分重音，`ci` 表示不区分大小写。比较与唯一约束都受排序规则影响，应按业务需要选择。MariaDB 的排序规则名称和支持范围不同。

PostgreSQL 通过连接选择数据库；下面的反斜杠命令是 **psql 客户端命令**，不能直接提交给普通 SQL 驱动：

```text title="psql"
\l
CREATE DATABASE learning;
\connect learning
\dt
\d users
\d+ users
SELECT version();
```

`CREATE DATABASE` 需要相应权限，并且不能在 PostgreSQL 事务块中执行。PostgreSQL 没有 `USE` 或 `CREATE DATABASE IF NOT EXISTS`，应用通常直接配置目标连接串。`\dt` 默认列出搜索路径可见的表，可以用 `\dt public.*` 指定 schema。

MySQL 的 `SHOW CREATE TABLE` 可以直接查看建表语句；PostgreSQL 的 `\d` 展示对象结构，导出 DDL 可使用 `pg_dump --schema-only --table=public.users learning`。

需要删除练习数据库时，两者都支持 `DROP DATABASE IF EXISTS learning;`，但要先确认库名。PostgreSQL 需要连接到另一个数据库，且目标库不能有阻止删除的活动连接。

## 建表、主键与注释

下面两段分别建立后续 CRUD 示例使用的 `users` 表。

```sql title="MySQL"
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY COMMENT '用户 ID',
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP, -- 保存本地日期时间，不携带时区
    CONSTRAINT uq_users_email UNIQUE (email)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COMMENT = '用户表';
```

```sql title="PostgreSQL"
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP, -- 按会话时区显示同一个时间点
    CONSTRAINT uq_users_email UNIQUE (email)
);

COMMENT ON TABLE users IS '用户表';
COMMENT ON COLUMN users.id IS '用户 ID';
```

PostgreSQL 的 `SERIAL` / `BIGSERIAL` 仍可用，本质是整数列、序列和默认值的组合；新表可以优先使用标准 SQL 的 identity。`BY DEFAULT` 允许显式提供主键，`GENERATED ALWAYS` 对显式写入限制更强。自动分配的 ID 可能因回滚或删除出现间隔，不应当作连续业务编号。

MySQL 需要引用标识符时使用反引号，PostgreSQL 使用双引号。PostgreSQL 未加引号的标识符会折叠为小写；统一使用小写加下划线可以减少引用问题。

## 数据类型与时间语义

| 用途 | MySQL | PostgreSQL |
| --- | --- | --- |
| 整数 | `TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT`、`BIGINT` | `SMALLINT`、`INTEGER`、`BIGINT` |
| 精确小数 | `DECIMAL(p, s)` | `NUMERIC(p, s)` / `DECIMAL(p, s)` |
| 近似小数 | `FLOAT`、`DOUBLE` | `REAL`、`DOUBLE PRECISION` |
| 布尔值 | `BOOLEAN` 是 `TINYINT(1)` 的别名 | 原生 `BOOLEAN` |
| 文本 | `CHAR(n)`、`VARCHAR(n)`、`TEXT` 系列 | `CHAR(n)`、`VARCHAR(n)`、`TEXT` |
| 二进制 | `BINARY`、`VARBINARY`、`BLOB` 系列 | `BYTEA` |
| JSON | `JSON` | `JSON`、`JSONB` |
| UUID | 常用 `CHAR(36)` 或 `BINARY(16)` | 原生 `UUID` |
| 日期与时间 | `DATE`、`TIME`、`DATETIME`、`TIMESTAMP`、`YEAR` | `DATE`、`TIME`、`TIMESTAMP`、`TIMESTAMPTZ` |

MySQL 的 `TEXT` / `BLOB` 上限是 65,535 字节，`MEDIUMTEXT` / `MEDIUMBLOB` 是 16,777,215 字节，`LONGTEXT` / `LONGBLOB` 是 4,294,967,295 字节；实际可传输大小还受客户端、`max_allowed_packet` 和资源限制。字符数取决于编码，不能把这些字节数直接当作中文字数。

MySQL 的 `BOOLEAN` 列仍可以存入 0、1 以外的整数；需要严格限制时添加约束。PostgreSQL 的 `JSONB` 适合需要索引和运算的 JSON 数据，但不会保留原始空白、键顺序等文本形式。

时间类型尤其需要区分：

- MySQL `DATETIME` 保存日期时间本身，不做会话时区转换；`TIMESTAMP` 会按会话时区与 UTC 之间转换，且可表示范围与 `DATETIME` 不同。
- PostgreSQL `TIMESTAMP` 默认指 `WITHOUT TIME ZONE`；`TIMESTAMPTZ` 保存一个时间点并按当前会话时区显示，不保留输入的原始时区名称。
- PostgreSQL 的 `now()` / `CURRENT_TIMESTAMP` 表示当前事务的开始时间。需要实际调用时刻可使用 `clock_timestamp()`，不要用事务时间测量代码耗时。

PostgreSQL 13+ 的 `gen_random_uuid()` 是内置函数，不需要仅为它安装 `pgcrypto`。更老的 PostgreSQL 版本可通过 `pgcrypto` 提供该函数：

```sql title="PostgreSQL 13+"
SELECT gen_random_uuid(); -- PostgreSQL 13+ 内置，生成随机 UUID

CREATE TABLE api_requests (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## 新增、更新与返回结果

两者都支持普通 `INSERT` / `UPDATE` / `DELETE`，PostgreSQL 还支持用 `RETURNING` 返回受影响行：

```sql title="PostgreSQL"
INSERT INTO users (username, email)
VALUES ('alice', 'alice@example.com')
RETURNING id, username, created_at; -- 同一语句直接返回新增行

UPDATE users
SET username = 'alice-new'
WHERE email = 'alice@example.com'
RETURNING id, username;

DELETE FROM users
WHERE email = 'alice@example.com'
RETURNING id;
```

MySQL 8.0 没有等价的通用 DML `RETURNING`，新增自增主键后，可以在**同一数据库连接**上读取：

```sql title="MySQL"
INSERT INTO users (username, email)
VALUES ('alice', 'alice@example.com');

SELECT LAST_INSERT_ID(); -- 必须与 INSERT 使用同一个连接
```

ORM 或驱动通常会提供新主键与受影响行数。不要在连接池中随意取另一条连接调用 `LAST_INSERT_ID()`。

按唯一键新增或更新的写法也不同。以下示例都依赖前面定义的唯一邮箱约束：

```sql title="MySQL 8.0.19+"
INSERT INTO users (username, email)
VALUES ('alice-updated', 'alice@example.com') AS incoming
ON DUPLICATE KEY UPDATE username = incoming.username; -- 主键或唯一键冲突时更新
```

```sql title="PostgreSQL"
INSERT INTO users (username, email)
VALUES ('alice-updated', 'alice@example.com')
ON CONFLICT (email)
DO UPDATE SET username = EXCLUDED.username -- EXCLUDED 指本次尝试插入的行
RETURNING id, username;
```

MySQL 的 `ON DUPLICATE KEY UPDATE` 可以被任意主键或唯一键冲突触发；PostgreSQL 可以明确指定冲突目标。MySQL 旧例子常用 `VALUES(username)` 引用待插入值，该形式自 8.0.20 起已弃用，可使用行别名。

## 函数、空值与大小写匹配

| 需求 | MySQL | PostgreSQL |
| --- | --- | --- |
| 当前日期 | `CURDATE()` / `CURRENT_DATE` | `CURRENT_DATE` |
| 从日期时间取日期 | `DATE(created_at)` | `CAST(created_at AS DATE)` / `created_at::date` |
| 当前日期时间 | `NOW()` / `CURRENT_TIMESTAMP` | `now()` / `CURRENT_TIMESTAMP` |
| 随机小数 | `RAND()` | `random()` |
| 空值替换 | `IFNULL(value, fallback)` 或 `COALESCE(...)` | `COALESCE(...)` |
| 大小写不敏感匹配 | 由列或表达式的排序规则决定 | 常用 `ILIKE` |

`CURDATE()` 不接收待转换的时间参数。以下是完整的日期和汇总查询，`COUNT`、`SUM`、`AVG` 等聚合函数在两个数据库中都可用：

```sql title="MySQL"
SELECT CURDATE() AS today,
       DATE('2026-07-08 12:30:00') AS date_part;

SELECT DATE(created_at) AS signup_date,
       COUNT(*) AS user_count
FROM users
GROUP BY DATE(created_at); -- 按日期聚合注册数
```

```sql title="MySQL / PostgreSQL"
SELECT COALESCE(SUM(amount), 0) AS total_amount -- 无有效金额时用 0 代替 NULL
FROM (
    SELECT 12.50 AS amount
    UNION ALL
    SELECT 7.50 AS amount
) AS payments;
```

`SUM` 忽略 `NULL`，没有参与计算的行时返回 `NULL`，可用 `COALESCE` 转为 0。`COUNT(*)` 统计行数，`COUNT(column)` 只统计该列非空的行。

PostgreSQL 可以直接用 `ILIKE '%alice%'`；MySQL 示例表是否忽略大小写，取决于实际使用的排序规则。需要跨数据库一致的用户名或邮箱唯一性时，应明确规范化规则和唯一索引设计。

## 索引：B-tree、全文与 JSON

两者默认的普通索引都适合 B-tree 的常见等值、范围和排序场景：

```sql title="MySQL / PostgreSQL"
CREATE INDEX idx_users_username_created_at
ON users (username, created_at);
-- 联合索引先匹配 username，再按 created_at 排序

EXPLAIN
SELECT id, username, created_at
FROM users
WHERE username = 'alice'
ORDER BY created_at;
```

索引顺序应从实际查询出发，例如先按用户名等值过滤，再按时间排序。是否使用索引仍由数据分布和执行计划决定；重复为已有唯一约束创建同列索引通常没有收益。

PostgreSQL 的 GIN 需要匹配支持的类型和运算符类。普通 `TEXT` 列不能直接照抄 `USING GIN (content)`；英文全文检索可以先生成 `tsvector`：

```sql title="PostgreSQL 全文检索"
CREATE TABLE documents (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    content TEXT NOT NULL,
    search_vector TSVECTOR GENERATED ALWAYS AS
        (to_tsvector('english', content)) STORED -- 写入时维护分词结果
);

CREATE INDEX idx_documents_search ON documents USING GIN (search_vector);

INSERT INTO documents (content) VALUES ('PostgreSQL indexes help search');

SELECT id, content
FROM documents
WHERE search_vector @@ plainto_tsquery('english', 'index search'); -- 查询使用相同分词配置
```

这里用的是英文词法配置，不应据此推断中文分词效果。模糊子串检索可以研究 `pg_trgm` 的 `gin_trgm_ops`，其索引和查询条件与全文检索不同。

`JSONB` 使用默认 GIN 运算符类的示例：

```sql title="PostgreSQL JSONB"
CREATE TABLE events (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payload JSONB NOT NULL
);
CREATE INDEX idx_events_payload ON events USING GIN (payload);

SELECT id
FROM events
WHERE payload @> '{"type": "login"}'::jsonb; -- 包含匹配，可使用上面的 GIN 索引
```

MySQL 有 `FULLTEXT` 索引，但分词器、匹配模式和查询语法与 PostgreSQL 不同；JSON 查询常按实际路径建立生成列或函数索引，不能把上述 GIN 语法直接迁移过去。

## 外键与约束变更

在已创建 `departments` 和 `employees`，且字段类型兼容的前提下，两者都可添加命名外键：

```sql title="MySQL / PostgreSQL"
ALTER TABLE employees
ADD CONSTRAINT fk_employees_department
FOREIGN KEY (department_id) REFERENCES departments(id); -- 两端字段类型需兼容
```

删除语法不同：

```sql title="MySQL"
SHOW CREATE TABLE employees;
ALTER TABLE employees DROP FOREIGN KEY fk_employees_department; -- MySQL 的删外键语法
```

```sql title="PostgreSQL"
ALTER TABLE employees DROP CONSTRAINT fk_employees_department; -- PostgreSQL 按约束名删除
```

PostgreSQL 可用 `\d employees` 查约束名；MySQL 可用 `SHOW CREATE TABLE`。外键背后的索引是否仍需保留要单独判断，不要把删外键等同于删除所有相关索引。MySQL 的 `CHECK` 从 8.0.16 起才开始实际执行，旧版本不能依靠它保证数据有效性。

## 用户与最小权限

以下是管理员执行的权限示例。`replace-with-a-local-password` 只是占位符，执行前替换。创建角色和撤销权限与业务表增删改是不同职责，应用连接不需要日常管理员权限。

```sql title="MySQL"
CREATE USER 'app_user'@'localhost'
IDENTIFIED BY 'replace-with-a-local-password';

GRANT SELECT, INSERT, UPDATE, DELETE
ON learning.* TO 'app_user'@'localhost'; -- 仅授予该数据库的业务读写权限

SHOW GRANTS FOR 'app_user'@'localhost';

REVOKE INSERT, UPDATE, DELETE
ON learning.* FROM 'app_user'@'localhost';
```

MySQL 的用户由用户名和主机共同标识，`'app_user'@'localhost'` 与 `'app_user'@'%'` 不是同一个账号。容器部署时应按真实来源地址配置，避免以为容器内的 `localhost` 是宿主机。

```sql title="PostgreSQL"
CREATE ROLE app_user LOGIN PASSWORD 'replace-with-a-local-password';
GRANT CONNECT ON DATABASE learning TO app_user;

-- 以下在 learning 数据库内执行
GRANT USAGE ON SCHEMA public TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA public TO app_user;
GRANT USAGE, SELECT
ON ALL SEQUENCES IN SCHEMA public TO app_user;

-- 对未来由当前对象所有者创建的表和序列生效
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT USAGE, SELECT ON SEQUENCES TO app_user;
```

PostgreSQL 的数据库连接权限、schema 使用权限、表权限和序列权限是分开的。`ALTER DEFAULT PRIVILEGES` 取决于**创建对象的角色**；应由实际建表角色执行，或者明确使用 `FOR ROLE`。它不补授已有对象权限。

删除示例账号时，MySQL 使用 `DROP USER 'app_user'@'localhost';`。PostgreSQL 使用 `DROP ROLE app_user;`，但要先处理各数据库内的权限依赖和对象所有权，不能把删角色当作无条件清理命令。
